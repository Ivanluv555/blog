> 你大概做过这些事：从网上下载一张图片，把它放到某个文件夹；用文档软件写下一段话，然后点击「保存」；收到朋友发来的压缩包，再把它「解压」。  

这些操作再普通不过。但如果追问几句，事情就开始有趣了：  
- 图片和文章看起来完全不同，为什么都叫文件？
- 一个文件夹里面还可以放文件夹，它们究竟是怎样组织起来的？
- 计算机只处理 0 和 1，为什么能知道哪些是文字、哪些是照片？
- 为什么有人说「万物皆文件」？鼠标、硬盘甚至程序之间的通信，也能叫文件吗？

## 1 数据不是文件，文件也不等于数据

> 先设想一个小实验:   
> 你在纸上写下「今天下雨了」，然后用手机拍一张照片。  
> 你现在有两份记录：一份是文字，一份是图像。  
> 它们表达的内容可能相近，但记录方式很不一样。  

计算机也一样。 **数据（data）** 是被记录、保存、处理的信息或符号； **文件（file）** 则是操作系统提供的一种组织和访问数据的方式。一个文件通常拥有名称、内容，以及大小、修改时间等元数据。

比如：
| 你看到的文件	| 里面大致记录的东西	| 常见扩展名|
| :-: | :-: | :-: |
| 日记	| 按某种字符编码记录的文本	| `.txt`、`.md` |
| 照片	| 像素信息与图像格式数据	| `.jpg`、`.png` |
| 音乐	| 编码后的音频数据	| `.mp3`、`.flac` |
| 压缩包	| 被压缩、打包的数据	| `.zip` |
| 程序	| 可供加载执行的指令及相关数据	| `.exe`、无扩展名等 |

同一份数据，不一定必须存在一个磁盘文件中。例如程序运行时的临时数据可能只存在内存里；网络上正在传输的数据也不一定已经保存成文件。反过来，一个文件也可能包含许多种数据：文档中可能同时保存文字、图片与样式信息。

数据是内容；文件是保存和访问内容的一种容器与抽象。

## 2 计算机怎样区分文字、图片和声音？

我们在前面提过，计算机内部依赖二进制表示信息。一个位（bit）可以表示 0 或 1；通常 8 个位组成一个字节（byte）。

但一串字节本身不会自动告诉我们「我是文字」或者「我是照片」。区别来自一套共同遵守的解释规则。
文字需要字符编码

例如，文本文件通常按照 UTF-8 等字符编码，将字符转换为字节。软件读取这些字节，再按相同的编码规则解释它们，屏幕上才会显示正确的文字。

如果写入和读取采用不兼容的编码，就可能出现所谓的「乱码」。这不是文字凭空损坏，而是双方理解字节的规则不一致。

### 2.1 图片需要文件格式

一张图片需要表示像素颜色、图像尺寸、压缩方式等信息。PNG 和 JPEG 都能存图片，但编码规则和压缩特点并不相同。

把 `photo.jpg` 重命名为 `photo.png`，一般不会把 JPEG 数据变成 PNG 数据。你只是改了名字，文件内部的内容仍旧遵循原来的格式。某些软件会检查文件内容而不是只看扩展名。
容易混淆： 扩展名是辨认文件类型的有用线索，但它并不是文件格式本身，更不能保证文件安全。

### 2.2 数据要有结构，软件才能使用

假如要保存三个人的姓名和年龄：

- 小王，19
- 小李，22
- 小陈，20

人可以读懂这段文本，但程序若要按年龄排序、查找某个人，就需要明确每一条记录与每个字段分别是什么。这就是我们接下来要讨论的数据结构。

## 3、数据结构：为什么「摆放方式」也很重要？

数据结构听上去是高深的编程术语，实际上可以先把它理解成：为了方便使用，我们如何组织数据，以及规定可以怎样操作它们。

想象你在整理书桌：纸张可以一张张排好，可以放进抽屉，也可以按类别装入不同的盒子。东西没有变，但取用和查找的便利程度变了。

### 3.1 列表与数组：按顺序排列

[`苹果` | `香蕉` | `橙子` | `葡萄`]

它适合记录一组有顺序的项目。你可以问「第三个是什么」，也可以从头遍历每个项目。

编程中的数组通常还具有更具体的存储和访问规则；不同语言里的列表实现可能不同。这里先抓住共同直觉：一组按顺序组织的元素。

### 3.2 字典或映射：用名字找到对应的值

- 姓名 → 小王
- 年龄 → 19
- 城市 → 上海

这种关系叫 **键—值（key–value）** ：用一个键找到它对应的值。手机通讯录、软件设置、JSON 对象，都能帮助我们建立这种直觉。

### 3.3 树：一层下面还有下一层

```
学习资料/
├── 历史/
│   └── 计算机简史.md
├── 终端/
│   ├── 基础命令.md
│   └── 练习.txt
└── 封面.png
```

这就是一种直观的树形组织：从一个根开始，逐层分支。文件夹可以包含子文件夹，所以它特别适合用来介绍树。

但要注意，真实文件系统还可能有符号链接、硬链接等机制，实际关系未必永远是一棵纯粹的树。入门阶段先理解「层级」就足够了。

### 3.4 队列与栈：顺序还可以决定处理方法

排队买票的人通常 **先到先服务** ，这类似 **队列（queue）** ；把盘子一张张叠起来，通常 **最后放上的先拿走** ，这类似 **栈（stack）** 。

这两种结构以后会在程序执行、任务处理等话题中反复出现。

| 结构 | 生活类比 | 最重要的特点|
| :-: | :-: | :-: |
| 列表 / 数组 |	排好的清单 | 有顺序 |
| 字典 / 映射 |	按姓名查电话 | 键与值对应 |
| 树 | 目录与子目录 | 分层组织 |
| 队列 | 排队 |	先进先出 |
| 栈 | 叠盘子 |	后进先出 |

这些结构不是只有程序员才需要关心。你在使用文件管理器、通讯录、播放列表、任务列表时，已经在接触它们带来的组织方式了。

## 4 文件夹和路径：计算机怎样找到一个文件？

当文件越来越多，只靠名字就不够了。你可能在两个不同文件夹里，都有一个叫 `notes.md` 的文件。

这时就要使用 **路径（path）** ，说明文件位于哪个位置。

> 例如：
> 学习资料/终端/基础命令.md
> 这个路径表示：从「学习资料」进入「终端」，再找到「基础命令.md」。

路径通常有两种理解方式：
- **绝对路径** ：从某个文件系统根位置出发，完整描述位置，例如 Linux 上的 `/home/alice/notes.md`，或 Windows 上的 `C:\Users\Alice\notes.md`。
- **相对路径** ：从当前所在目录出发，例如 `notes.md` 或 `../images/cover.png`。

这里的 `..` 往往表示「上一级目录」。不同操作系统的路径书写方式可能不一样，但通过层级定位资源的思想是相通的。

另外，文件夹不只是「纸箱」的比喻。操作系统中的 **目录（directory）** 本身也是一种特殊的文件系统对象，用于组织名称与对应的文件系统条目；具体如何存储，由文件系统实现决定。

## 5 什么是文件系统？

文件可以有名字、大小、位置，也可以创建、删除、移动。真正 **为这些操作提供规则** 的，是 **文件系统（file system）** 。

你可以把它想象成一座图书馆的管理制度：一本书放在哪里、如何编号、怎样找到它、谁可以借阅，都要有规则。

常见的文件系统包括 Windows 经常使用的 NTFS，以及 Linux 上常见的 ext4、Btrfs 等。它们在设计、支持的功能与存储方式上有所区别。

一个文件系统通常需要处理：

1. 名称与目录：怎样定位文件。
2. 数据存储：文件的内容保存在哪里。
3. 元数据：大小、时间、权限等信息怎样记录。
4. 访问与一致性：多个程序访问和修改数据时，怎样尽可能维护正确性。

因此，硬盘是保存数据的设备，文件系统是组织与管理这些数据的一套机制。二者不是一回事。

> 文件并不总对应硬盘上一段连续的位置。现代文件系统会用不同方式记录数据块与文件之间的关系。此处不需要掌握具体实现。

## 6 终于来到「万物皆文件」

现在我们已经知道普通文件和目录是什么了。接下来谈一句非常有名、但也非常容易被误解的话：**Everything is a file**（万物皆文件）。

它常被用来概括 Unix 系统的设计哲学：尽量为 **不同资源** 提供 **类似文件** 的访问接口。

例如，在许多类 Unix 系统中：

- 普通文件可以通过文件描述符来读写。
- 终端设备可以通过类似的读写接口进行交互。
- 管道（pipe）可以让一个程序把输出传给另一个程序。
- 许多设备在 `/dev` 目录下有对应的设备文件。
- Linux 的 `/proc` 和 `/sys` 提供了一些可通过文件式接口查看的内核与设备信息。

这样一来，程序 **不必为所有对象发明完全不同的操作方式** 。它们可以尽可能使用类似 open、read、write、close 的接口，虽然具体支持的操作和行为仍然因对象而异。
但是，它并不意味着「所有东西真的都是普通磁盘文件」

- `/dev` 中的设备文件，不等于在磁盘上保存了一整份设备内容。
- `/proc` 中许多内容由内核动态生成，并非普通的持久文件。
- Unix 套接字、网络套接字等资源可以借助文件描述符操作，但不意味着都表现为一个可在目录中找到的普通文件。
- 文件式接口也不能代替所有系统调用与设备专用控制接口。

所以更准确的说法是：许多资源可以被抽象为可以打开、读取、写入或关闭的对象，从而拥有相似的操作模型。

> 这是一种工程思想：用统一的抽象，把复杂差异藏在接口后面。

一个很有趣的例子：把输出写进 **看起来不该写进的地方**

在 Linux、macOS 等类 Unix 系统中，`/dev/null` 是一种特殊设备：写入其中的数据会被丢弃。

你以后可能看到这样的命令：

```bash
some-command > /dev/null
```

它大致表示：运行 `some-command`，并把标准输出重定向到 `/dev/null`。

从表面上看，任何输入其中的内容都会被丢弃，但实际上，Shell 可以把原本显示在终端中的输出，连接到另一种具有文件式接口的对象。

现在不必执行这条示意命令，也不必记住每个符号。等学到终端、重定向与管道时，我们会回来亲手验证。

## 7 为什么这跟 Claude Code、Codex 有关系？

你可能会觉得，我们讲文件，为什么又扯到 AI 编程工具？

因为一个 AI 编程代理面对软件项目时，首先接触的往往不是「一个漂亮的应用」，而是一组目录、文件、配置、代码和命令执行结果。

它需要知道：

- 哪个文件是项目的说明书（常见为 README.md）。
- 哪些文件是源代码，哪些是图片或配置。
- 要修改哪一个文件，修改前后如何比较。
- 一个目录下的路径是相对哪里计算的。
- 命令执行后，输出与错误信息从哪里来。

这也是为什么，理解文件与数据组织，不仅能帮助你管理照片和文档，也会帮助你判断 AI 到底修改了什么。

不过，会访问文件不代表 AI 可以随意读取一切。真实工具受到运行环境、权限配置与用户授权的约束。授予访问前，需要考虑隐私和敏感数据。

## 8 动手实验：自己建立一棵小小的目录树

这一实验只需要图形文件管理器，不要求你会写命令。

1. 在你容易找到的位置创建一个文件夹，命名为 my-computer-lab。
2. 在里面创建 notes、images 和 projects 三个文件夹。
3. 用纯文本编辑器创建 notes/hello.txt，写入一句话并保存。
4. 复制一张你有权使用的图片到 images 中。
5. 在文件管理器里打开「显示文件扩展名」的选项（不同系统入口不同），观察 .txt 与图片扩展名。
6. 在副本上尝试只修改扩展名，观察软件是否依然能够正确识别文件；最后恢复原来的名字。

你最终应该得到类似这样的目录：

```
my-computer-lab/
├── notes/
│   └── hello.txt
├── images/
│   └── example.jpg
└── projects/
```

如果你的图片不是 JPEG，请保留真实扩展名，不必强行改成 .jpg。

你创建了几个文件夹？几个文件？hello.txt 里的文字属于数据，还是文件？

> 文字是数据，hello.txt 是承载这份数据的文件。

## 9 试着回答这五个问题

1. 为什么同样是字节，软件却能把它们解释成文字或者图片？
2. 把 .jpg 改名为 .png，图片格式会自动改变吗？
3. 「树」这种数据结构与文件夹有什么相似之处？
4. 为什么说「硬盘」与「文件系统」不是一回事？
5. 「万物皆文件」指的是统一的接口思想，还是所有资源都真的是磁盘上的普通文件？

## 10 小结

- 数据是信息的表示；文件是保存和访问数据的一种抽象。
- 字节需要遵循编码或格式规则，才能被正确解释。
- 数据结构让信息更容易组织、查询和处理。
- 目录与路径帮助我们定位文件；文件系统负责组织和管理文件。
- 「万物皆文件」是 Unix 家族的重要设计理念，但不能按字面理解成「所有东西都是普通文件」。
